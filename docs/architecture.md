# 架构设计说明

## 核心理念：记忆与投喂分离

### 问题背景

大模型的上下文窗口是有限的。即使窗口越来越大，实际有效信息承载量也远低于理论值。学术研究表明（Chroma Research 2025 Context Rot），所有测试的前沿模型都随输入长度增加而性能下降。

传统对话工具将"存储"和"投喂"混为一谈——所有消息既存储在对话历史中，也全部送入模型。这导致：

1. 上下文越长，性能越差
2. 无关信息持续干扰推理
3. 无法精确控制模型"看到什么"

### TCK 的解决方案

TCK 将上下文管理拆分为两个独立层：

```
┌─────────────────────────────────────────┐
│              用户交互层                   │
│         (对话界面 / API 调用)             │
└──────────────┬──────────────────────────┘
               │
       ┌───────┴───────┐
       │               │
       ▼               ▼
┌─────────────┐ ┌─────────────┐
│   记忆层     │ │   投喂层     │
│ (Memory)    │ │ (Feeding)   │
│             │ │             │
│• 永久完整存储│ │• 按策略裁剪  │
│• 本地数据库  │ │• 精确子集    │
│• 可搜索回溯  │ │• 发送给模型  │
│• 可恢复     │ │             │
└─────────────┘ └─────────────┘
```

### 记忆层（Memory Layer）

- **存储**：所有消息永久完整保存
- **位置**：本地数据库
- **能力**：搜索、回溯、恢复、导出
- **特点**：不受上下文窗口限制，是"全量记忆"

### 投喂层（Feeding Layer）

- **来源**：从记忆层中按策略裁剪
- **去向**：发送给大模型
- **能力**：六种裁剪策略，随时切换
- **特点**：精确控制模型实际看到的内容

### 设计优势

1. **解耦**：存储和投喂独立，不需要在"保留历史"和"控制长度"间取舍
2. **可控**：模型每次看到什么，完全由用户决定
3. **可复现**：投喂内容确定，相同输入得到一致输出
4. **安全**：敏感信息可排除在投喂层之外，但仍保留在记忆层

## 理论基础

| 研究成果 | 核心机制 | TCK 对应方案 |
|---------|---------|-------------|
| 上下文漂移 (Context Drift) | 早期设定被后续消息稀释 | headTail 保持头部设定 |
| 上下文污染 (Context Pollution) | 无关/错误信息持续干扰 | manualCut 屏蔽污染源 |
| 注意力稀释 (Attention Dilution) | 上下文越长注意力越分散 | slidingWindow/fieldCut 精简内容 |
| 前摄干扰 (Proactive Interference) | 旧信息干扰新推理 | manualCut 截断旧上下文 |
